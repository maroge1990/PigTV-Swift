## 1. Working rules

- **Push-to-main (Mark, 23 Sept).** Work on `main` in this folder. Claude may `git pull --rebase` and **push to `origin/main`**
  without asking each time. Before every push: the tvOS build and tests pass, plus an iOS build when shared code changed.
  **`xcode-select` on the MacBook points at the Command Line Tools, so every Xcode command needs `DEVELOPER_DIR`** (don't change
  the system setting):
  ```bash
  export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
  xcodebuild test -project PigTV.xcodeproj -scheme PigTV -destination 'platform=tvOS Simulator,name=Apple TV,OS=26.5'
  xcodebuild build -project PigTV.xcodeproj -scheme PigTV -destination 'generic/platform=iOS Simulator'
  ```
  Never force-push. `.gitignore` keeps Xcode and Finder user state out of commits.
- **CI (A0.3).** `.github/workflows/ci.yml` runs on every push to `main` and on pull requests: it selects the runner's
  newest Xcode (failing with a clear message if it is older than the client's minimum), builds for the iOS Simulator, and
  runs the tvOS tests on an Apple TV simulator it finds or creates. It cannot be exercised locally; treat a red run on
  GitHub as equivalent to a local test failure.
- **Bump the build number** (`CURRENT_PROJECT_VERSION`, both app targets in `project.pbxproj`) once per session that changes
  app code, so Settings → Version identifies the installed copy. Current: **36**; next: **37**.
- **Crash lessons (builds 21–25, §7):** never call an AVKit-only API (a category on an AVFoundation class, e.g.
  `AVPlayerItem.externalMetadata`, `UIWindow.avDisplayManager`) on tvOS without checking it exists (AVKit is linked explicitly
  for tvOS); **nothing may await before `replaceCurrentItem`/`play()` except the resolve and the audio session**; every
  AVFoundation/KVO/notification callback is `@Sendable`/nonisolated and hops to the main actor (Swift 6).
- **New playback code gets a test in the real-playback harness** (`PigTVTests/RealPlaybackTests.swift`, §4): two crashes reached
  the TV because no test played a stream through the app's own code.
- **Swift 6 language mode** for the app and the Top Shelf extension (Mark: on); keep pure helpers `nonisolated` so the Swift 5
  test targets can call them.
- **Organisation:** the lead Claude session delegates implementation to sub-agents and reviews every diff before it's pushed.
  Device-dependent items end with numbered test steps for Mark and become *Verified* only on his report.
- Other internet use still needs Mark's approval: browsing, SDK or dependency downloads, and **contacting the deployed server**.
  Driving the simulator UI (attach, screenshots, input) only when Mark asks in that message; routine checks are `xcodebuild` runs.
- Never send `force: true` automatically: viewer or recording takeover needs an explicit choice. Browsing and focus must never
  acquire a provider stream. Preserve same-origin auth, media URL allow-listing, capability negotiation and release-before-switch.
- Server changes are made in the server repo under its blueprint §2; client-visible server changes appear in
  `../PigTV/docs/SWIFT-CLIENT-HANDOFF.md` §5, so read it at each session start.

**At a glance (build 32).** Tabs: **Home** (opens first) · **TV Guide** · **Sport** (with the server's `sportsEvents`) ·

|---|---|---|---|

- **UIKit guide grid (A2.1, build 20; the only tvOS grid since build 27, and the iPad's since build 29):** `GuideView` shows `GuideGridView` on tvOS and on iPad (regular width; the SwiftUI grid — `timelineGrid`, `GuideTimelineRow` — was **deleted in build 29**, so there is one grid) (`UIViewControllerRepresentable` → `GuideGridViewController`), keeping its header, filters, summary area and all sheets/covers; the Now button sits in the header next to Earlier/Later (build 22). One `UICollectionView` with a custom `GuideGridLayout`: section = channel row, item 0 = the channel tile (pinned left via the content offset), items 1…n = programmes at `x = (start − model.window) × pointsPerSecond` over the whole loaded 24 h (2 h = the timeline width), or one day-wide "no programme information" placeholder; a now-line decoration; cells clipped at the channel column with the clipped amount passed to the cell (`GuideGridAttributes.leadingClip`) so titles stay visible. The time header is a separate strip view above the rows that follows `contentOffset.x` (so rows never scroll under it). Horizontal position is owned by the grid: `GuideGridCollectionView` locks `bounds.origin.x`, so the focus engine's own scroll-into-view cannot move it sideways; the grid moves by whole half-hour columns with its own 0.2 s ease-in-out display-link animation (none with Reduce Motion). Focus is the collection view's own: `canFocusItemAt` makes finished programmes unfocusable and, in rows other than the focused one, only the Up/Down target (the programme under the time anchor) focusable; `shouldUpdateFocus` plans the column move for Left/Right and redirects Left-onto-the-tile ahead of the live baseline (step back / return to live) via `indexPathForPreferredFocusedView`. Pure maths (positions, clipping, sticky tile, column reveal, vertical target, left step) is in `GuideGridMath.swift`; the row filter is `GuideRowFilter` (shared with the SwiftUI grid). Rows are applied with a plain data source (append → `insertSections`, anything else → `reloadData` + focus restored by identity), not diffable snapshots, because the real guide has ~18 000 channels × ~30 programmes. Files: `GuideGridMath.swift`, `GuideGridLayout.swift`, `GuideGridCells.swift`, `GuideGridView.swift`; tests `GuideGridMathTests`, `GuideGridNavigationUITests` (no launch argument since build 27; `GuideNavigationUITests`, the SwiftUI grid's test, was deleted).

  **Build 22:** Now moved into the header's button row (before Earlier/Later, new guide only). Up from the grid's top row lands on it: the grid's `shouldUpdateFocus` refuses the engine's move out of the top (no next index path, heading up) and calls `GuideGridActions.leaveUp`, which sets GuideView's `headerNowFocused`.   **Build 33 — the guide no longer hits a wall moving forward (Mark, live testing: "as if it hasn't loaded any further").**
  Root cause: `GuideGridLayout.loadedDuration` (the grid's content width) was never fed from the model and stayed at the
  hard-coded `GuideNavigation.loadedDuration` (24 h) forever, so the grid could not scroll or focus past it regardless of how
  much programme data existed; `GuideNavigation.needsReload` compared the viewport to the same fixed `window + 24 h`, and a
  reload it did trigger (e.g. the header's Later button) ran `loadGuide()` with `keepVisible: false`, blanking every row.
  Now: `BrowseModel.guideLoadedUntil` (published) tracks how far programme data actually reaches, starting at
  `window + loadedDuration` and pushed forward by `extendGuideForward()`; `GuideGridView` carries it down as
  `loadedDuration` (`guideLoadedUntil − origin`), so the layout's content width grows with it — `GuideGridViewController.
  update(from:)` treats a duration-only change as layout-only (`invalidateLayout`, no reload, no scroll/focus change).
  `GuideView.setViewport` calls `GuideNavigation.needsExtension` (true within `extendThreshold`, 6 h, of the loaded edge) to
  kick off `extendGuideForward()` in the background well before the grid could run out of columns; `needsReload` now takes an
  explicit `until:` (`guideLoadedUntil`, not always `window + 24 h`) for a genuine jump outside the loaded range (Jump to…),
  which still reloads but always with `keepVisible: true`. `extendGuideForward()` pages through every channel exactly like
  the initial load, for the next `loadedDuration` slice, and merges the results into existing rows
  (`GuideNavigation.mergeProgrammes`, deduped by start time — `GuideChannel.withProgrammes` swaps just the programme list) —
  never replacing them — while trimming programmes older than `GuideNavigation.pastTrimMargin` (24 h) to keep memory bounded
  over a long session; `GuideGridViewController.apply(rows:)` gained a third case (`extendedOnly`, alongside `appendOnly` and
  the full reload) that only `reloadSections` for the channels whose programme count actually changed. Ends for good
  (`guideEnded`), with nothing left to retry, once a slice comes back with no programmes — the provider's guide has ended.
  `GuideRowsInput` gained `programmesVersion` (from `BrowseModel.guideProgrammesVersion`, bumped on every merge) since a
  channel's identity/count alone does not change when its programmes are extended in place, so the existing row-filter
  memoisation would otherwise never notice. A failed guide page (initial load or an extension) is retried with backoff
  (`GuideNavigation.guidePageRetryDelays`, 8 s then 12 s — 3 attempts across ~20 s) before it surfaces; the error banner's
  Retry (`BrowseModel.retryGuide`) resumes from `guideOffset`/`guideCursor` — wherever paging stopped — instead of
  restarting the whole guide. The on-disk guide cache is unchanged (`saveCache` still runs once, right when the initial
  load's paging finishes, before any extension, so it stays about one day). Measured on 1 000 channels (offline fixture,
  `PIGTV_UI_TEST_CHANNELS=1000`): merging one 24 h slice into every row took **~200 ms** end to end (network round trip +
  JSON decode + the single rebuilt-array `guide` assignment), well under the UI's stall budget; tab-switch and grid-navigation
  perf tests (`TabSwitchUITests`, `GuideGridNavigationUITests`) show no regression. Pure functions and tests:
  `GuideNavigation.needsExtension`/`mergeProgrammes`/`trimmed`/`needsReload(until:)`/`guidePageRetryDelays` (`ContractChecks.
  swift`); `BrowseModel.extendGuideForward`/`retryGuide` against a fake paged/flaky guide endpoint, including the 1 000-channel
  timing (`GuideModelTests.swift`); a UI test on the offline fixture (`GuideFixtures.forwardHorizon`, 26 h, so there is real
  next-day data with no server to extend from) moves right past 24 h and confirms real programmes keep appearing
  (`testMovingRightPast24HoursReachesTheNextDaysProgrammes` — on the old code this hangs the app: "process main thread busy
  for 30.0 s", confirming the wall).

## 6. Shared contracts and coordination

- Guide rows use `id/sourceId/name/logo/category/tvgId/programmes`, with programme `startTime/endTime` in **milliseconds**. Marker `startMs/endMs` also use milliseconds.
- Favourites writes use bare channel IDs; source-qualified IDs remain useful for local UI identity. Read favourites from `library/favourites`.
- **Resolve errors (C-B, A1.3):** a non-2xx `playback/resolve` whose `error` starts with `The provider refused this channel`, `The provider did not respond` or `This channel is not available` becomes `PigTVError.message` (trimmed to 300 characters; shown by the player's error screen). Any other text, any text containing `://`, and any non-resolve path keep the generic mapping (`APIClient.displayableResolveError`). No flag: a text match.
- Resolve sends `capabilities.segmentedDelivery = true`. “transcode” strategy can mean video/audio copy into HLS, not re-encoding.
- Approved media paths: `/api/proxy/stream`, `/api/transcode/…`, `/api/recordings/…` (`/api/remux` was retired by server 0103 and removed from the client's allow-list and strategy lists in A0.1); tokens on approved media URLs, bearer on session DELETE. Do not broaden URL acceptance to fix playback.
- Recording playback: bearer-authenticated `/api/recordings/{id}/playback`; MP4 response with same-server `media.mp4`, token query and byte-range seeking. Async preparation is additive and opt-in. C-E: with `recordingHls` the answer may be `{url: …/index.m3u8, container: "hls", durationSec, inProgress}` (contract checks cover it).
- Flags: the server's `/api/info` flags and what this client does with each are tabled in
  `../PigTV/docs/SWIFT-CLIENT-HANDOFF.md` §0. Read: `viewerConflict` (409 handled by type regardless), `epgLogoFallback`,

## 7. Deferred choices and crash lessons

Testing ownership: the client agent runs `xcodebuild` builds and simulator tests; Mark runs physical Apple TV, iPad, iPhone and
multi-device checks (Xcode installs on the downstairs TV). Simulator results do not establish real-provider playback or
hardware behaviour. Contacting the deployed server needs Mark's approval.

- No session keep-alive planned: recovery is needed regardless and idle reclamation protects recordings. Revisit only if actual pause usage requires it.
- HEVC recording playback remains unverified on hardware. Old server `.native.mp4` sidecars may carry `hev1`; any cleanup is a separate approved server operation, not a client workaround.
- Minimum OS versions/supported devices and distribution/versioning policy need agreement before release (today: iOS/tvOS 26.5, development signing only). Do not inherit the server build number as the Swift build number.
- AirPlay, PiP and background playback remain outside current scope; preserve existing restrictions until session ownership supports them.
- Avoid speculative VOD/series work (the server removed VOD in 0122).

**Crash on channel start (builds 21–23), fixed in builds 24–25.** The real cause, from the device console (Mark, test 1.9):
`-[AVPlayerItem setExternalMetadata:]: unrecognized selector`. `externalMetadata` is an AVKit category on AVPlayerItem.
Once build 21 retired the last AVKit player on tvOS, AVKit was no longer loaded, and setting it crashed the moment a
channel started. `PlaybackModel.setExternalMetadata` now sets it only when the selector exists, and a test reproduces the
crash on the old code. Build 25 also **links AVKit explicitly for tvOS** (`OTHER_LDFLAGS[sdk=appletv*] = -framework AVKit`): `UIWindow.avDisplayManager` (HDR/50 Hz switching) is an AVKit category too and would have crashed next. `testAVKitCategoriesAreAvailableOnTV` guards both. **Lesson:** never call AVKit-only API on tvOS without checking it exists; the simulator tests
missed this because no test started a real player item.

Build 23 also moved the app target back to Swift 5 on a wrong diagnosis (the KVO-isolation theory). **Build 28 returned to
Swift 6** (Mark approved) with every KVO/AVFoundation callback explicitly `@Sendable`/nonisolated (see §4 Swift 6) and the
real-playback harness exercising them. Verified on the TV (R2.15: no crashes across live channels, switching, Last channel and
a recording).

## Multi-provider failover, client side (build 36, work package A1)

Spec: `../PigTV/docs/MULTI-PROVIDER-BRIEF.md` (§2.6, §2.8, C-J, C-K). Server flags `providers` and `providerReminders` in
`ServerInfo.Features`; everything is additive and absent flags change nothing.

- **C-J (`ResolveProvider`, `PlaybackDecision.provider`):** decoded tolerantly (a malformed object is just nil). `PlaybackModel.provider`
  is set at each resolve; `StreamStats.parts` (the Labs stream info line, tvOS) adds "Provider: Trex (backup)" for a backup and
  "switched from primary" when `failover` is true. The ordinary primary play adds nothing (matches the line's density).
- **C-K (`ProviderReminders.swift`, `ProviderReminderModel.swift`, `ProviderReminderBanner` in `ContentView.swift`):**
  `AppModel.checkProviderReminders()` runs once signed in, on `scenePhase == .active` and when the player closes; needs
  `providerReminders`, never runs while `playerPresented`, and shows at most one banner per local day per device
  (`UserDefaults` `pigtv.providerReminderDay`, set only when a banner is actually shown; an empty answer or a failed request
  leaves the day unused). The banner is an **overlay** on the root view (no cover, so no nested-cover focus trap, W6) and is dismissed
  after 15 s, by its OK button (iOS/iPadOS) or when playback starts. **On tvOS it is deliberately not focusable** (no button):
  it cannot take or trap focus and goes away by itself. Text: "Trex expires Mon 30 Mar. Renew it with the provider; PigTV picks up
  the new date by itself."; past expiry "expired on …"; several providers in one sentence.
- **Recovery allowance:** `PlaybackModel.recoveryUsed` is renewed when a failure arrives after `recoveryResetInterval` (120 s) of
  unbroken good playback since the last recovery (`goodPlaySince`, set in `playbackStarted` after a recovery, cleared by a stall,
  a failure and Retry; `clock` is injectable). Still at most one re-resolve per failure; a failure inside 2 min of a recovery ends in
  the error as before.
- **Tests:** `ProviderFailoverTests` (8: provider shown/absent, line formats, reminders once a day / not during playback / flag absent /
  empty and failing answers / auto-dismiss and "expired", the recovery renewal against real playback), contract checks.
  `FakePigTVServer` gained `reminders:`, `client(extraFeatures:)` and `decision(provider:)`.
- **Not verified:** the banner's look and placement on a real TV, iPad and iPhone (no visual check made).
